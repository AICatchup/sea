# V69 — 実形状に基づく接地と崖の立体比較

2026-10-13。Chromeの実際のWebGL描画を比較。実写同等、全箇所の改善、実測センチ精度は未達成。

## 通常版に採用

- 低木は元の葉の頂点から支持形状を求め、斜面への埋まりをロード時に補正。配置数と根の水平位置を保持し、幅の縮小は最大30%、根と地表の距離は最大8cm。4618本を検査して2514本を補正した。233本は解消できず、診断に残す。追加の崖メッシュまで含む完全な支持判定ではない。
- 崖際の既存スキャン岩は、実頂点の一部が地形へ埋まるまで法線方向へ限定的に移動。120個中15個を最大25cm補正。元のスキャンの形状・UV・材質・数を保持し、描画と衝突へ同じ行列を渡す。32%という条件はサンプル頂点の比率で、体積や全接触面の保証ではない。
- 計算はロード時だけ。追加テクスチャや毎フレームの支持計算はない。`shrubground=0`、`outcropseat=0`で各補正前を比較できる。

同じ時刻・カメラの近距離比較では、斜面から不自然に突き出す低木の葉が局所的に収まった。広い視点で目立つ退行は見つからなかった。岩の見た目の差は小さい。独立レビューもこの限定した採用を支持した。接地改善を全体の写実性の達成に読み替えない。

## 崖の比較候補

DEV専用 `cliffvolume=jointplanes` は、不均等な面・稜線・分岐する割れ目を実3Dへ反映した候補。124760三角形、閉じた一体形状。元のV32と周辺の埋設境界を保持し、CPUで壁5経路・斜め10経路を遮断、岸と船の3経路を開放した。

Chromeの5方向比較では上部の角張った形状は見えるが、改善は局所的。大きく丸い崖と砂浜への滑らかな接続帯が残るため、通常版はV32を維持した。候補を実測した泊の岩肌とは扱わない。参照した[式根島観光協会の泊海水浴場](https://shikinejima.tokyo/play/beach/tomari_beach/)の写真は、ゲーム素材として転載していない。

## 検証

- 全564テスト、型検査、本番ビルドと単体HTML生成が成功。最後のロード時診断追加後も関連6テストとビルドが成功。
- 初回の全テストでDEV判定のNode読込エラーを検出。`import.meta.env`を安全に判定するよう直し、全体を再実行した。
- Chromeの1280×720、高画質、同じ初期位置、波を再生した180フレームの比較で、平均間隔は補正前31.2497ms／補正後31.2480ms、p95は双方31.6ms、診断は双方32fps。この場面での低下は観測されなかった。GPU単体時間や全場面の性能保証ではない。影・反射の更新周期が違う単一フレームのdraw数は比較指標にしていない。
- 通常のクリックとW入力で初期位置から浅瀬と崖沿いを歩行。歩行状態のまま到達した記録であり、今回の記録は泳ぎ・潜水・乗船を証明しない。アプリのChrome errorログは空。
- 5視点の静止比較と葉の近距離比較は `checks/v69`。固定カメラは通常移動の成功証拠ではない。崖内部へ入った診断カメラは受入画像から除外した。

## 継続する不足

崖の巨大な丸い面、砂浜と岩の接続形状、斜面の葉の残る埋まり、右岸の白い一様な面、近距離の葉・幹・岩の材質差が残る。次の工程は既存の細かな模様を重ねることより、地形・可視メッシュ・床の一致を保ちながら大形状と接続帯を置き換えること。海の既存品質は保持し、複数の目線と実景を使って判断を続ける。

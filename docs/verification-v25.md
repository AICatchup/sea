# V25 — 遠い樹冠の密度（2026-10-06）

実装は `db7195e59e7e6cc4ff8d889466d66e5b421e83a3`、基準はV24公開main `07f93afd38d7ff5f30fbfb2a3f202e2c8683c047`。通常表示に採用した、泊周辺の遠景植生の限定的な改善。実写同等の達成ではない。

## 差と変更

[観光協会の泊海水浴場](https://shikinejima.tokyo/play/beach/tomari_beach/)を再確認し、以前取得したGoogleの実景写真も実表示した。岩の上を低く密な緑が覆う実景に対し、元の画面は黒い細片と裸の地表が目立った。実景との撮影位置・光・時刻は一致しないため、画素一致や現地測量の証拠にはしない。

松の既存CC0モデルから葉がある場所を求め、一株42個以下の小さな湾曲した小枝パッチを中・遠景へ補った。既存のプロジェクト生成アトラスを使い、カメラへ向きを追従させない。パッチは薄い面による近似で、一本一本の立体的な針葉や現地の樹種を再構成したものではない。

- 近景は元のモデルをそのまま使う。中・遠景も元の葉・枝・幹を保持する。補助は45～72mで徐々に現れる。
- 低木には補助を適用しない。木・低木の配置行列、地形、幹の衝突形状は保持する。
- 補助は追加の影を落とさず、元の幹・葉が影を担当する。距離で消えている葉が近くへ影だけを落とす回帰を避ける。
- 透明な画像の黒い余白が縮小時に葉色へ混ざらないよう、alphaで重み付けした線形光のmipmapを使う。alpha自体は線形に保持する。裏から通る光と空からの散乱は軽量な近似で、実測した葉の光学特性ではない。

通常は有効。`?branches=0` で補助なしと比較できる。通常UIに新しい切替や移動モードは追加しない。

## 独立レビューと修正

一人の新しいレビュー担当へ、参照写真、5視点の変更前後、コードと撮影時の情報を渡した。最初の候補は、近くの松と低木にも補助を重ねており、rear視点の葉が大きな板や壁に見えるとしてNEEDSFIXとなった。元の近景を保つ現在の構成へ修正した。同じ担当が修正後の5枚を確認し、**ADOPT AS LIMITED IMPROVEMENT**と判定した。[レビュー記録](checks/v25/review.md)を参照。

残る問題として、遠くの葉束が一部で丸い塊として見えること、元の近景の葉が黒い細片状で疎らなことを指摘されている。これらを写真同等と呼ばない。

## 検証

- 302テスト、TypeScript、本番ビルド、素材埋込HTMLの生成が成功。大きいbundleの警告は継続。
- 開始地点、岩際、水際、高所、後方を同じカメラ・1280×720・高品質・昼で比較。海面の履歴が異なるので、水色や反射の改善判定には使わない。海中・羽伏浦正面・シークレットも通常採用版で描画を確認。
- 3種類の元の木について、近景のgeometry保持、幹proxyの一致、有限な位置・単位法線、補助の外形上限を確認。撮影時の衝突数は全て3,240、幹数は3,098。低木の三角形数は全5視点で一致した。
- 松の表示三角形数は開始地点で約195万→221万、後方で約291万→335万。360万の松の上限内で、近景の三角形数は変更前と一致した。全体の描画回数は反射・影の更新周期で変わるため、単一フレームの比較から高速化は主張しない。
- タッチコントローラーと同じ移動入力で、開始位置から水際へ20秒連続して歩いた。位置の直接変更は使っていない。波は停止して植生の変化を確認した。21秒の実canvas映像を1280×720・30fpsのMP4（630フレーム）へ保存し、抽出フレームとブラウザで最後の0:21/0:21までの再生を確認。
- この区間のブラウザRAFは1,260間隔、中央値16.7ms、95百分位16.8ms、33.4ms超は0件。録画の負荷を含むこの環境での観察であり、GPU単体の計測、スマートフォンや全島の性能保証ではない。物理キーボード長押しによる検証とも区別する。
- 撮影APIは、元の視点へ戻す前に描画情報を保存するよう修正した。画像と異なる場所のモデル数を記録しないための変更。ブラウザエラー・警告は今回の通常採用版で0件。
